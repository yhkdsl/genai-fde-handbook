§ 1.3가장 큰 차이 — 타입이 강제되지 않는다

Java에서 오면 이게 제일 먼저 발을 건다.

def add(a: int, b: int) -> int:
    return a + b

add("hello", "world")   # 실행된다. "helloworld" 반환

타입힌트는 런타임에 아무것도 하지 않는다. 주석에 가깝다. 컴파일러가 잡아주던 것을 이제 아무도 안 잡아준다.

그래서 Python 진영은 두 가지로 이 구멍을 메운다. 둘 다 써야 한다.

도구시점Java 대응역할

실무에서 중요한 것은 Pydantic 쪽이다

LLM 애플리케이션에서 가장 자주 깨지는 지점은 모델이 뱉은 JSON이다. 스키마를 지키라고 시켜도 안 지킬 때가 있다. 이때 Pydantic이 경계에서 걸러주지 않으면 이상한 값이 시스템 안쪽까지 들어온다.

Ch.4의 Structured Output이 바로 이 문제를 다룬다. 지금 Pydantic에 익숙해지는 게 거기서 그대로 쓰인다.

§ 1.4Spring Boot 서비스를 FastAPI로

아래는 실제로 실행해서 검증한 코드다. Spring의 주요 구성요소가 어디로 갔는지 주석으로 표시했다.

설정 — @ConfigurationProperties 대응

from functools import lru_cache
from typing import Annotated
from fastapi import Depends
from pydantic import Field
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_prefix="APP_",      # APP_PROJECT_ID 환경변수를 읽는다
        env_file=".env",
        extra="ignore",
    )
    project_id: str = "local-dev"
    location: str = "us-central1"
    model: str = "gemini-2.5-flash"
    max_output_tokens: int = Field(default=1024, ge=1, le=65535)

@lru_cache                       # 앱 생애주기 동안 1회만 생성 = 싱글턴 Bean
def get_settings() -> Settings:
    return Settings()

SettingsDep = Annotated[Settings, Depends(get_settings)]

application.yml + @ConfigurationProperties + @Validated 가 한 클래스에 들어갔다. max_output_tokens에 붙은 ge=1, le=65535는 @Min/@Max와 같고, 환경변수가 잘못되면 애플리케이션이 아예 시작하지 않는다. Spring과 동일한 fail-fast다.

DTO — Bean Validation 대응

from typing import Literal
from pydantic import BaseModel, Field

class AskRequest(BaseModel):
    question: str = Field(min_length=1, max_length=2000)   # @NotBlank @Size
    style: Literal["short", "detailed"] = "short"          # enum

class AskResponse(BaseModel):
    answer: str
    model: str
    input_tokens: int
    output_tokens: int
    cost_usd: float

엔드포인트 — @RestController 대응

from fastapi import FastAPI, HTTPException

app = FastAPI(title="ch12-verify")

@app.get("/healthz")
def healthz(s: SettingsDep) -> dict[str, str]:
    return {"status": "ok", "project": s.project_id, "model": s.model}

@app.post("/ask", response_model=AskResponse)
async def ask(req: AskRequest, s: SettingsDep) -> AskResponse:
    if req.style == "detailed" and len(req.question) < 5:
        raise HTTPException(status_code=422, detail="detailed 모드는 질문이 더 길어야 함")
    in_tok, out_tok = len(req.question.split()), 42
    return AskResponse(
        answer=f"[stub:{req.style}] {req.question}",
        model=s.model,
        input_tokens=in_tok,
        output_tokens=out_tok,
        cost_usd=estimate_cost(in_tok, out_tok),
    )

여기가 Spring과 결정적으로 다른 지점이다. req: AskRequest와 s: SettingsDep라는 타입 표기만으로 바디 파싱·검증·의존성 주입이 전부 결정된다. 컨테이너 스캔도, @Autowired도 없다. 함수 시그니처가 곧 선언이다.

§ 1.5asyncio — 가장 오해가 잦은 부분

Java 경력자가 가장 많이 틀리는 지점이다. async를 "빨라지는 것"으로 이해하면 반드시 사고가 난다.

Java 스레드 모델과 무엇이 다른가

Java (전통적 서블릿) 요청 1 ──▶ [스레드 1] ──── DB 대기 (스레드가 블록된 채 놀고 있음) 요청 2 ──▶ [스레드 2] ──── API 대기 → 동시 요청 수만큼 스레드. 스레드는 비싸다 (~1MB 스택) Python asyncio 요청 1 ─┐ 요청 2 ─┼──▶ [단일 스레드 + 이벤트 루프] 요청 3 ─┘ await 를 만나면 그 자리를 양보하고 다른 요청을 처리 → 대기 중에 스레드를 붙잡지 않는다

핵심은 await는 "여기서 기다린다"가 아니라 "여기서 자리를 양보한다"는 것이다. Java 21의 Virtual Thread가 지향하는 바와 목적이 같다. 다만 Python은 그것을 명시적으로 써야 한다.

그래서 이런 함정이 생긴다

@app.post("/bad")
async def bad():
    time.sleep(3)        # ❌ 동기 블로킹 — 이벤트 루프 전체가 멈춘다
    return {"ok": True}  #    이 3초 동안 다른 모든 요청이 대기한다
규칙 하나만 기억한다

async def 안에서는 블로킹 호출을 하지 않는다. requests 대신 httpx.AsyncClient, time.sleep 대신 asyncio.sleep, 동기 DB 드라이버 대신 async 드라이버를 쓴다.

불가피하게 동기 라이브러리를 써야 하면 await asyncio.to_thread(무거운_함수, 인자) 로 감싼다.

참고로 FastAPI에서 def(async 없이)로 선언하면 FastAPI가 알아서 스레드풀에서 돌린다. 블로킹 코드를 써야 한다면 차라리 async를 빼는 게 안전하다. 위 /healthz가 그 예다.

CompletableFuture 대응 — 실측

import asyncio, time

async def io(name, sec):
    await asyncio.sleep(sec)
    return name

# 순차 — Java: f1.join(); f2.join(); f3.join()
await io("a", 0.3); await io("b", 0.3); await io("c", 0.3)

# 병렬 — Java: CompletableFuture.allOf(f1, f2, f3).join()
await asyncio.gather(io("a", 0.3), io("b", 0.3), io("c", 0.3))

# 타임아웃 — Java: future.orTimeout(100, MILLISECONDS)
async with asyncio.timeout(0.1):
    await io("slow", 5)     # TimeoutError
실행 결과 (검증됨) 순차 await : 0.90s asyncio.gather : 0.30s ← 3배 asyncio.timeout: TimeoutError 정상 발생

이게 왜 이 핸드북에서 중요한가. LLM 호출은 한 번에 수 초가 걸리는 I/O다. RAG에서 여러 검색을 동시에 태우거나(Ch.6 하이브리드 검색), 에이전트가 여러 툴을 병렬 호출할 때(Ch.10) gather를 쓰느냐 아니냐가 응답 시간을 몇 배로 갈라놓는다. Google JD가 말하는 "latency" 요건이 여기서 결정된다.

# Vertex AI 공개 가격, USD per 1M tokens (2026-07 확인)
PRICE_IN, PRICE_OUT = 0.30, 2.50    # gemini-2.5-flash

def estimate_cost(input_tokens: int, output_tokens: int) -> float:
    return round(input_tokens / 1e6 * PRICE_IN
                 + output_tokens / 1e6 * PRICE_OUT, 8)
모델입력 / 1M출력 / 1M캐시된 입력 / 1M
gemini-2.5-flash$0.30$2.50$0.03
gemini-2.5-pro (≤200K)$1.25$10.00$0.13
gemini-2.5-pro (>200K)$2.50$15.00$0.25

출력이 입력보다 8배 비싸다(flash 기준). 그리고 캐시된 입력은 10분의 1이다. 이 두 사실이 나중에 프롬프트 설계를 바꾼다 — 긴 시스템 프롬프트를 캐싱하고 출력을 짧게 유도하는 게 비용에 직결된다. Ch.4에서 다시 다룬다.
